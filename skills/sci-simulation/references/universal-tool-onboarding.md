# 通用计算模拟规范：新工具上手 8 步（Universal Tool Onboarding）

> dsh-science v0.9.0 · sci-simulation 附带规范。
> 设计参考：AcademicForge `claude-science/compute-env-setup` 的**验证阶梯**思想（import 通过 ≪ 内核分发见证 ≪ 智能体照文档逐字执行）与"按层归因"诊断表、以及其 compute_details 登记（dossier）机制。本地参照件：`research/academicforge/skills/claude-science/compute-env-setup/SKILL.md`（repo: HughYau/AcademicForge，MIT）。本规范为面向远端 HPC/模拟场景的原创中文改写与扩展（8 步 + 产出物/完成判据 + dossier 字段清单），未照搬原文。
> 适用对象：simulator 角色（以及任何需要在新计算环境里使用未内置 dossier 的工具/模型/代码包的成员）。
> 定位：本插件的 5 个内置 dossier（GROMACS/Gaussian/Quantum ESPRESSO/LAMMPS/ASE，见
> `references/tool-dossiers/`）覆盖高频工具；**遇到未内置的新工具时，必须完整走完本规范 8 步，
> 才允许把该工具的结果写进任何结论或文章蓝图 claim。** 不得凭训练记忆直接写输入文件。

## 原则（三条铁律）

1. **数值以远端实际安装版本的官方手册为准**——记忆里的参数/单位/默认值一律视为待核验。
2. **验证阶梯不可跳级**——冒烟未过不进见证，见证未过不进生产（与 sci-simulation 总协议一致）。
3. **一切核验留痕**——每步的版本号、URL、命令、输出摘录写进会话笔记，失败也要记录失败证据。

## 8 步规范

### 第 1 步：版本核验
- 用 `sci_ssh_exec` 在目标机器上确认：软件名、精确版本号、构建变体（编译器/MPI/GPU 后端）、
  依赖库版本（Python/CUDA/BLAS 等）。
- 把 `--version`/`module show`/`conda list` 等原始输出摘录进笔记。
- 若远端有多个版本（modulefile/conda env），先与队长确认用哪个，并记录选择理由。
- **产出物**：版本核验记录（软件/精确版本号/构建变体/关键依赖版本 + 原始命令输出摘录）。
- **完成判据**：拿到的版本号来自远端实机输出而非记忆或最新文档——远端实际版本 ≠ 最新文档版本时，
  以远端为准并在笔记中显式记下这一差异。

### 第 2 步：手册章节定位（URL 登记）
- 取得**该精确版本**的官方手册/文档对应章节，给 URL；离线机器上找安装目录的 docs/ 或
  `sci_file_fetch` 拉取。
- 重点读：输入文件语法、单位制、默认值、已知限制（Limitations/FAQ）、并行行为。
- 官方没有手册的小众工具：以源码内 examples/tests 为手册替代，同样给路径；两处都没有 →
  向队长报告"该工具不可按规范上手"，不得硬写。
- **产出物**：手册 URL 登记表（工具/版本/章节标题/URL/查阅日期；离线则为安装目录路径）。
- **完成判据**：每个后续要用到的输入段/关键字都能指回一个具体手册章节 URL，而非"网上说"。

### 第 3 步：最小输入模板
- 从官方示例（examples/、tests/、文档 quickstart）起步，改到本任务的最小问题规模。
- 只改必须改的参数；每处修改注释"为什么改"。
- 禁止从记忆手写整份输入文件。
- **产出物**：最小输入模板文件（每处修改带注释）+ 模板来源路径/URL。
- **完成判据**：模板可追溯到官方示例原文，diff 中每一处改动都有"为什么改"注释。

### 第 4 步：冒烟（smoke）
- 极小规模（秒~分钟级）走通完整管道：输入 → 求解 → 输出可解析。
- 检查点：正常退出码、无 NaN/负守恒、日志无 ERROR/WARN 级异常、输出字段与手册一致。
- 冒烟失败 → 走第 7 步诊断（按层归因），修完重来。
- **产出物**：一次完整冒烟运行的输入/日志/输出文件 + 运行记录（耗时、规模、退出码）。
- **完成判据**：管道端到端跑通且输出可被脚本解析；四项检查点全绿；全程秒~分钟级。

### 第 5 步：见证（witness）
- 中等规模，结果必须**定量对照已知答案**：解析解、官方 benchmark、文献算例、或粗网格极限外推。
- 量化误差（相对偏差、收敛阶）写进笔记；误差不可接受 → 诊断，不许带病进生产。
- 新工具第一次跑通见证后，把关键参数与判据写进第 8 步 dossier 草稿。
- **产出物**：见证对照记录（基准来源/数值对照表/相对偏差或收敛阶）+ 见证输入文件归档。
- **完成判据**：误差在事先声明的可接受阈值内（阈值本身写进记录）；对照基准可引用、可复跑。

### 第 6 步：生产（production）
- 按 sci-simulation 提交纪律：`sci_job_submit`（审批）、walltime = 3× 预估、参数显式写入
  `.job_env`（不留默认值）、产物统一 out/、低频监控（`sci_job_status`）。
- 生产前检查点：随机种子/初始条件已记录、可断点续算、磁盘配额足够。
- **产出物**：生产作业的作业脚本 + 显式参数清单（.job_env）+ out/ 产物 + 监控记录。
- **完成判据**：所有物理/数值参数在作业脚本或 .job_env 中显式可查（无隐式默认）；作业正常结束
  且产物完整；实际 walltime 反哺预估供下次校准。

### 第 7 步：诊断（按层归因）
- 失败先分类（能本地复现就本地复现），按四层归因，从下往上排查、一次只动一层：
  - **L1 输入格式层**：语法错误、单位制错、关键字拼错/版本改名、文件组织不符 → 症状多为解析报错
    或参数被静默忽略。
  - **L2 物理参数层**：力场/泛函/边界条件/步长/网格等参数选错或超适用范围 → 症状多为能算但结果
    离谱、不收敛、发散。
  - **L3 资源层**：内存/磁盘/墙钟/进程数/线程绑定不足或冲突 → 症状多为 OOM、超时、异常降速
    （对照 compute-env-setup 经验：线程数要显式设，别信 os.cpu_count()）。
  - **L4 科学设定层**：问题本身的尺度/近似等级/坐标系不适合该工具 → 症状为换参数无效，需换工具
    或重述问题。
- 另记环境类干扰（模块冲突/驱动版本/并行库 ABI）与版本差异（升级引入的行为变化），归入最接近层。
- 对照官方 FAQ/issue tracker；把"现象→原因→修复"三元组记入笔记与 dossier 的已知坑。
- 同一错误修复后必须从对应验证阶梯层级重跑（冒烟失败修完重冒烟；生产中发散则退回见证）。
- **产出物**：诊断记录（症状原文/归属层/根因/修复动作/重跑结果）+ 修好的输入或环境配置。
- **完成判据**：每个失败都有唯一归属层与可执行修复，且已按阶梯从对应层级重跑通过；
  "现象→原因→修复"已同步进 dossier 草稿。

### 第 8 步：登记 dossier
- 用 `references/tool-dossiers/_TEMPLATE.md` 起草新工具档案：必查项、输入结构、已知坑、
  收敛判据、引用格式（含本规范 1-7 步积累的版本号/URL/参数/误差数据）。
- 保存到插件 `skills/sci-simulation/references/tool-dossiers/<tool>.md`（若成员无写权限，
  把 dossier 全文发回队长，由队长/用户落盘归档）。
- 登记完成后，本工具后续使用走内置 dossier 快路径；dossier 数值仍以远端版本手册为准。
- **产出物**：新工具 dossier 文件（或发回队长的 dossier 全文）。
- **完成判据**：dossier 字段清单（见文末）逐项非空或标"待核验"；第 1/2/5 步的版本号、URL、
  误差数据已落入对应字段；下次同工具任务可直接按 dossier 执行。

## 与既有机制的关系

- 内置 5 dossier（GROMACS/Gaussian/QE/LAMMPS/ASE）：已是"8 步走完后的登记产物"，直接使用。
- 角色技能库（`role-skills/simulator/`，INDEX.md 索引）：目录里的工具类 skill（如 cantera、
  OpenFOAM/HPC）提供**领域参数与流程知识**，不替代本规范——新工具仍需 8 步核验该 skill 的
  建议 vs 远端实际版本。
- 队长派工：涉及"没用过的新工具"时，预期成员回报中包含第 1/2/5 步的证据（版本号、手册 URL、
  见证误差）；缺任何一项即退回补齐。

## 附：dossier 模板字段清单（第 8 步逐项核对）

新工具档案（`references/tool-dossiers/<tool>.md`，基于 `_TEMPLATE.md`）必须覆盖以下字段；
暂无内容的写"待核验"，不允许留空：

1. **工具名与一句话定位**——是哪类求解器/代码包，解决什么问题。
2. **必查项清单**——写输入前逐项确认的硬性检查（对应第 1-3 步沉淀）。
3. **核验登记**——软件名 / 远端实际精确版本号 / 版本核验命令与日期 / 手册章节 URL（第 1、2 步产物）。
4. **输入结构**——稳定输入组织方式；标明哪些是规范要求、哪些只是惯例；模板来源路径/URL。
5. **典型最小算例**——冒烟算例的输入/预期输出摘要与运行耗时量级（第 4 步产物）。
6. **基准与收敛/质量判据**——见证用的基准（解析解/benchmark/文献算例）、可接受误差阈值、
   收敛检查方法（第 5 步产物）。
7. **生产纪律**——推荐的资源形状（进程/内存/墙钟）、walltime 预估口径、参数显式化清单、
   断点续算方式（第 6 步产物）。
8. **已知坑**——"症状 → 根因（归属层）→ 处置"三元组，逐条记录（第 7 步产物）。
9. **不可用边界**——该工具明确不适合的问题类型/规模（L4 科学设定层结论）。
10. **引用格式**——程序引用（含版本对应文献）+ 方法/力场/泛函/赝势引用，逐条给 DOI 或 URL。
